how t3code hands work to agents — and keeps the chat in its own app

no agent ever gets a visible terminal. the server starts each agent cli as a hidden background process and talks to it over pipes: json-rpc for codex, the claude agent sdk for claude. the chat you see is not the agent's output — it is the server's own event log, saved in sqlite and streamed to every client. the phone, the web app and the desktop app are all thin clients of that log.

the important split: the orchestrator only decides what happened, and every side effect (start a turn, interrupt, answer an approval) is a queued outbox job written in the same transaction. if the server dies between deciding and doing, the job is still there.

01 · no terminal, just pipes

codex — the server spawns codex app-server as a child process and wires stdin/stdout straight into a typed json-rpc client; stderr is dropped. shell: false everywhere except windows. no pty.

claude — @anthropic-ai/claude-agent-sdk query() in streaming-input mode: prompts are pushed into a queue the sdk reads as a live input stream. the sdk starts the claude cli itself.

others — acp agents, opencode serve, pi --mode rpc, the cursor sdk. nine provider drivers in total.

02 · one adapter shape for every agent

ProviderAdapterV2.openSession() returns a runtime with ensureThread, resumeThread, startTurn, steerTurn, interruptTurn, respondToRuntimeRequest, rollbackThread, forkThread and an events stream.

codex shares one process across many threads; claude gets one session per app thread. the capability flag supportsMultipleProviderThreadsPerSession decides.

03 · a message becomes a run

the model: AppThread → Run (one user-visible turn) → a tree of ExecutionNodes, plus ProviderThread, ProviderTurn, TurnItem, RuntimeRequest, Checkpoint.

clients only send commands: thread.create, message.dispatch, run.interrupt, thread.stop, runtime-request.respond, checkpoint.rollback, thread.fork, provider.switch.

04 · talking to a busy agent

message.dispatch carries a dispatchMode:

start_immediatelyqueue_after_activesteer_activerestart_activedefer_start

on the phone this is the “steer it now / queue after this turn” pair above the composer.

05 · what the chat is made of

every provider is normalised into one list of turn items:

user_messageassistant_messagereasoningcommand_executionfile_changedynamic_toolweb_searchfile_searchtodo_listproposed_planapproval_requestuser_input_requestsubagentcheckpointerrorcompactionhandoff

assistant text is split into display chunks only at markdown-safe boundaries, and tool updates are coalesced so only the latest per call is kept — cheap to stream to a phone.

06 · approvals

runtime modes: approval-required, auto-accept-edits, auto, full-access (the default). codex asks through item/commandExecution/requestApproval and friends; claude through the sdk's canUseTool callback.

the adapter emits a runtime request and waits. a client answers with runtime-request.respond: accept, acceptForSession, acceptAlways, decline or cancel. pending requests are stored, so they survive a reconnect.

07 · surviving flaky networks

storage is sqlite through node:sqlite: an events table with a sequence number, projection tables, the outbox and command receipts.

subscribeThread{threadId, afterSequence} sends a snapshot, then numbered events, then a synchronized marker. a client that drops resumes from its last sequence. resending the same commandId returns the stored receipt and runs nothing twice.

08 · lifecycle

sessions open lazily on the first turn and are released after 30 idle minutes — later while background work is pending, up to a 4-hour cap.

a crashed session is deliberately not restarted. unfinished work is marked finished; the next command opens a fresh session and resumes the agent's own conversation (resume / thread/resume).

09 · worktrees and checkpoints

each thread has a branch and a worktreePath; a launch picks root, existing_worktree or a new worktree{baseRef}.

checkpoints are hidden git refs (refs/t3/orchestration-v2/checkpoints) built with a temporary GIT_INDEX_FILE, write-tree and commit-tree. diffs come from them; rollback restores the files and asks the provider to roll back its conversation too.

10 · reaching it from elsewhere

pairing links and qr codes (t3 pair, t3 serve --host), scoped tokens, short-lived websocket tickets so long-lived tokens stay out of socket urls, and a scope check on every rpc.

transport: tailscale, ssh tunnels, or a relay with sign-in. mobile push and live activities go through the relay. the in-app terminal is a separate node-pty feature, not how agents are run.

what cellar desk takes from it

left: what t3code does. right: the cellar version. rows marked “new” are not in t3code.

server on the pc owns processes, files and sqlite

a small cellar desk daemon (node, tray app) owns the agents, the worktrees and its own event log. the phone is a thin client.

one websocket rpc + http snapshots

the same, over tailscale. when the pc can't be reached, the phone drops the task into cellar's supabase as a row and the daemon picks it up — the mcp edge function and per-machine agent tokens already exist.

thread → run → turn items

a run can start from a cellar entry: the agent claims it, appends lines marked as its own, and asks questions through the same “waiting on you” inbox.

runtime request → respond

the approval panel pinned above the nav islands, plus a push. answer on the phone or the pc — the first answer wins, retries are safe because of the commandId.

runtime modes

three words on the new-task sheet: ask first · edits ok · full access.

new · quick commands

rebuild, deploy and apk are plain jobs, not agent turns. they go through the same outbox and stream back as command_execution items, so the phone renders them like any other run.

new · previews

the dev server runs on the pc and is exposed to the phone's webview over the tailnet. deploy runs npm run deploy:web only after you've looked.

new · live screen

a separate video channel (screen out, touch and keys in), opened only when the phone asks and the pc allows it. kept apart from the event log so a dropped stream never touches a run.

in-app terminal (node-pty)

left out on purpose. from the toilet or the stove you want results and decisions, not a shell.

not confirmed from source

whether spawns on windows set windowsHide (that lives inside the effect library, not in t3code), and the claude cli's exact stdio settings (inside the agent sdk). worth testing on your pc that no console window flashes.
